# fxn-cms

Strapi 5 backend behind the FXN network of affiliate, commerce and content
sites, plus the sourcing, keyword research and AI generation tooling that feeds
those sites.

One CMS serves every property. Content types are namespaced per site
(`nxt-post`, `bls-post`, `nxtsmarthome-post`, and others) rather than split
across instances. The `commerce-site` collection is the registry that ties a
property to its content types, commerce types, editorial brief and dashboard
links.

## Current state

`main` includes the site-scoped AI Writer work merged in PR #14 on 2026-08-22:

- AI Writer no longer writes every generated draft to `api::article.article`.
  It resolves the target collection from the selected site's `commerce-site.contentTypes`
  registry.
- `commerce-site.aiWriterBrief` is the per-site system prompt used by AI Writer.
  Sites without a brief are explicitly warned in the admin UI instead of silently
  getting generic travel copy.
- AI Writer opens with `?site=`, `?topic=` and `?keyword=` context from the site
  dashboard and keyword research screen.
- The form supports one title per line, so a user can create several drafts in
  one run while each article is still generated by its own model request.
- Optional cover handling was added: pick from the site's media library, or ask
  the writer to generate a cover for each draft.
- The site dashboard now has per-site keyword research backed by DataForSEO and
  the host job runner.
- The dashboard's Recently edited panel now resolves real Strapi 5 publish state
  instead of labelling live documents as `DRAFT` because their draft row has a
  null `publishedAt`.

## Layout

| Path | What it is |
|---|---|
| `backend/strapi-deploy/` | The CMS. Docker Compose for Strapi 5.52.1 and Postgres, 38 content types, 6 custom admin plugins. |
| `backend/nxt-sourcing/` | Next.js product-sourcing UI on `:3005`, plus the CLI scripts that do catalogue, offer and keyword work. |
| `backend/ai-writer-cli/` | Standalone generators and enrichers for fxnseo.com, run from cron and by hand. |
| `backend/scripts/` | One-off migration helpers, mostly WordPress to Strapi. |
| `frontend/` | Legacy CRA app. Not the live frontends; those live in separate repos under `/opt/projects/*`. |
| `tests/`, `test_reports/`, `test_result.md` | Test and QA artifacts for this deployment repo. |

The job runner that executes sourcing and research jobs from the Strapi admin
lives outside this repo at `/opt/nxt-job-runner` in its own private repo. It
holds only a `RUNNER_TOKEN`; API credentials stay in `backend/nxt-sourcing/.env.local`.

## Running the CMS

```sh
cd backend/strapi-deploy
docker compose up -d            # start existing image
docker compose up -d --build    # required after any source change
docker compose logs -f strapi
```

Strapi listens on `127.0.0.1:8888`, proxied to `cms.fxnstudio.com`.

The image is baked, not mounted. Source is copied in at build time, so editing
`strapi/src/**` changes nothing until the image is rebuilt. `restart` is not
enough, and neither is `up -d` without `--build`; the old code will keep booting.

### Environment

Four `.env` files are relevant:

| File | Read by | Notes |
|---|---|---|
| `backend/strapi-deploy/.env` | Docker Compose and the Strapi container | The production CMS env file. Compose interpolates `${VAR}` from here. |
| `backend/strapi-deploy/strapi/.env` | Non-container local Strapi only | Ignored by Docker. Do not treat it as production truth. |
| `backend/nxt-sourcing/.env.local` | Sourcing UI, sourcing scripts and runner jobs | Merchant, DataForSEO, Anthropic/OpenAI and catalogue credentials live here. |
| `backend/ai-writer-cli/.env` | Standalone fxnseo generators | Separate from the CMS plugin. |

`.env` files are gitignored. After editing `backend/strapi-deploy/.env`, run
`docker compose up -d`; a restart will not re-read the Compose environment.

Important values used by the latest plugin work:

```text
ANTHROPIC_API_KEY        direct Claude calls from CMS/plugin code
ANTHROPIC_MODEL          optional global model override
RUNNER_URL               defaults to http://172.18.0.1:4310
RUNNER_TOKEN             bearer token for host runner calls
```

DataForSEO credentials for keyword research are used by the runner-side
`keyword-research` job, not by the Strapi container directly.

## Site registry

`commerce-site` maps each property to the collections that belong to it. The
load-bearing field is `contentTypes`, keyed by role. Each role is an array because
a role can have more than one source:

```jsonc
"contentTypes": {
  "posts": [
    { "uid": "api::nxtsmarthome-post.nxtsmarthome-post" },
    { "uid": "api::nxtsmart-post.nxtsmart-post",
      "filter": { "site": "nxtsmarthome.com.au" } }
  ]
}
```

The `filter` is not optional for shared types. `nxtsmart.homes` and
`nxtsmarthome.com.au` share `nxtsmart-post`, split by that type's own `site` enum.
Drop the filter and each site reports the other's rows as its own.

AI Writer now uses the same registry to choose where drafts are created. That is
intentional: the dashboard and writer cannot disagree about what belongs to a
site.

Other important `commerce-site` fields:

| Field | Purpose |
|---|---|
| `name`, `slug`, `domain` | Site identity and plugin routes. |
| `niche`, `country` | UI labels and default research context. |
| `contentTypes` | Site-owned content collections and filters. |
| `aiWriterBrief` | Per-site system prompt for AI Writer. |
| `siteStatus` | Active/inactive state. |

Seed or re-seed sites with:

```sh
cd backend/strapi-deploy/strapi
node scripts/seed-commerce-sites.mjs --dry-run
node scripts/seed-commerce-sites.mjs
```

The seed is idempotent by domain.

## AI Writer

AI Writer is a Strapi admin plugin that creates draft posts with Claude. It is
site-scoped and should normally be opened from a site dashboard tile or from a
keyword research result:

```text
/admin/plugins/ai-writer?site=<site-slug>&topic=<title>&keyword=<keyword>
```

### How targeting works

1. The form requires a site. It takes the initial site from `?site=` or, if there
   is only one available site, defaults to that.
2. The server resolves the site's posts target from `commerce-site.contentTypes`.
3. The draft is created in that target collection, not in a generic fallback.
4. The writer only sends fields declared by the target schema. This matters
   because `tags` can be JSON on one type and a relation on another.
5. Generated posts remain drafts. They must be reviewed, assigned/checked and
   published by a person.

A missing site is an error. Silent defaults are avoided because the old default
sent drafts to `api::article.article`, a collection no live site reads.

### Per-site brief

`commerce-site.aiWriterBrief` is the system prompt. It should say who the site is
writing as, who the audience is, the market-specific facts it must respect, and
what it must never claim.

For example, a smart-home site brief should mention Australian homes, 230V power,
local standards, Australian retailers and Australian Consumer Law. Without that,
generic copy can drift into travel or US-market assumptions.

The admin page warns when the selected site has no brief. The fallback still
exists for compatibility, but it should not be treated as acceptable for a live
property.

### Form behavior

- `Titles` accepts one title per line. Each line becomes one draft.
- Category options are loaded from the selected site's context, so they cannot
  belong to a different property.
- The old `Destination` field is relabelled by site niche, for example `Device or brand`
  on smart-home/tech sites.
- Keywords can be prefilled from keyword research.
- A cover can be selected from the site's media library, or generated per draft
  when no cover is selected.
- Title suggestions can be requested for a selected category before generation;
  they are editable suggestions, not writes.

## Keyword research

The site dashboard includes keyword research at:

```text
/admin/plugins/site-dashboard/<site-slug>/keywords
```

The screen starts a paid DataForSEO-backed job through the host runner and polls
for the result. It is deliberately a two-step async flow because DataForSEO plus
model judgement can outlive a normal proxy request timeout.

Routes added by the site-dashboard plugin:

```text
POST /site-dashboard/sites/:slug/keywords        # start a run
GET  /site-dashboard/sites/:slug/keywords/:runId # poll result
```

Measured and inferred values are kept separate:

| Value | Source |
|---|---|
| Search volume | DataForSEO / Google Ads data |
| Competition | DataForSEO |
| CPC | DataForSEO |
| Relevance | Model judgement using the site's brief/context |
| Intent | Model judgement |
| What to publish | Model judgement |

The UI labels volume as `searches/mo`, not visitors. Ranking for a query does not
mean the site receives the whole search volume.

Keyword result actions carry site context forward:

- `Create article` opens AI Writer with `site`, `topic` and `keyword` query params.
- `Find products` opens commerce-product-finder with the same site and query.
- `Copy keyword` copies the exact keyword.

Search volume defaults to Australia (`location_code` 2036) in the keyword tooling.
Keep that explicit for AU catalogues; several older scripts in the same family
used US defaults.

## Publish state in Strapi 5

Strapi 5 draft rows have `publishedAt: null` even when a published version of the
same document exists. That means reading rows with `status: 'draft'` and checking
`publishedAt` labels everything as draft.

The dashboard handles this by checking for a matching published row by
`documentId`. Types without draft-and-publish are treated as live. Match that
pattern when adding dashboard lists or status chips.

The relevant behavior exists in:

```text
site-dashboard/server/src/services/content-list.js
site-dashboard/server/src/services/site-stats.js
```

## AI client

Anthropic is called directly. The system previously routed Anthropic-model work
through OpenRouter, which added markup and a second prepaid balance that could run
dry and break `cost: 'ai'` jobs with HTTP 402.

The shared client for sourcing scripts is:

```text
backend/nxt-sourcing/scripts/lib/anthropic-chat.mjs
```

Use it rather than hand-rolling requests:

```js
import { askForJson } from './lib/anthropic-chat.mjs';

const { title } = await askForJson({
  system: 'You rewrite ecommerce product titles.',
  prompt,
  schema: {
    type: 'object',
    properties: { title: { type: 'string' } },
    required: ['title'],
    additionalProperties: false,
  },
});
```

Things worth preserving:

- Do not send `temperature` to current Anthropic models; they reject it with 400.
- JSON comes from `output_config.format` and a schema, not from regex extraction.
- Default model is `claude-opus-5` unless overridden by script-specific env vars
  such as `KEYWORD_RESEARCH_MODEL`, `PRODUCT_TITLE_REWRITE_MODEL`,
  `PRODUCT_DESCRIPTION_REWRITE_MODEL`, or global `ANTHROPIC_MODEL`.
- Rewrite scripts keep OpenClaw and OpenAI fallbacks. Select with
  `PRODUCT_TITLE_REWRITE_PROVIDER=openclaw|anthropic|openai`.

## Sourcing and runner jobs

The sourcing scripts live in `backend/nxt-sourcing/scripts/`. Most are also
registered as jobs in `/opt/nxt-job-runner`, so they can be triggered from the
Strapi admin. Examples include `keyword-research`, `check-offers`,
`rewrite-title`, `fetch-offers`, and `post-*` jobs.

```sh
cd backend/nxt-sourcing
node scripts/keyword-research.mjs --seed="smart doorbell" --site=nxtsmart.homes
node scripts/check-offer-liveness.mjs --dry-run
```

Conventions to match:

- `--dry-run` before anything that writes.
- Report what will change before changing it.
- Exit non-zero when a run that should have done work did nothing.
- Keep paid jobs user-triggered unless they are intentionally scheduled.

## Scheduled work

Check `crontab -l` on the host. Content-related entries:

- `sync-fxnseo-cron.sh` runs every 15 minutes and publishes Strapi `fxnseo-post`
  entries to the live fxnseo.com blog. It is idempotent and does not generate.
- `tick-populators.mjs` is currently paused. It reads enabled `content-populator`
  rows and dispatches their generator jobs. This is the scheduled path that
  creates content.

Price, coupon and stock refreshes run through cronmanager:

```sh
cron-wrapper.sh <id>
```
